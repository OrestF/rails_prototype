# COAX app setup from template

Take a new project from an empty directory to a running, green application that follows COAX standards:

1. the COAX AI configuration imported **first**, so every later step runs under the company's engineering rules
   for that technology;
2. `PROJECT_SETUP_CHECKLIST.md` in the project root, derived from the COAX Wiki "Project setup" pages and ticked
   off as each item is actually verified;
3. the application generated from the official template for its technology;
4. a verification loop that keeps fixing and re-running until the app builds and runs, tests and linters are
   green;
5. the app left running (backend or web dev server, or a mobile app on a simulator or emulator), and
   `AGENTS.md` generated by `/init-agents`.

Usually the GitHub repository does not exist yet when the app is created, so everything happens locally. Steps
that need the repository (pushing, the AI config sync pull request, CI runs, SonarQube) become checklist items
with an owner. COAX policy says a competence lead must review any repository setup they did not do themselves;
that review is the last checklist item and is never ticked by the skill.

## Where the app is created

The app is created in the **current working directory**: the directory this skill runs in is the project root.
Never ask for a path, and never create the app anywhere else. Check the directory first:

- It must be new: empty, or holding only tooling such as `.git` (no commits yet), `.claude/settings*.json`,
  `.idea/`, `.vscode/`, `.DS_Store`. If it holds anything else, stop and ask: this skill sets up new apps, and
  generating over existing code destroys it.
- It must not be the template repository itself (`rails_prototype`, which contains `template.rb` and this skill).
  Ask the user to open a session in the new project's directory instead.

The checklist is the same for every stack: its items describe outcomes, and its "What the items mean for your
stack" table says how each one translates (hook tool, linters, what "runs locally" means, whether Docker applies).
For a stack without a full reference, follow the technology-independent steps as written (1, 2, 7 and 9), and do
the rest by hand from the template's own README, ticking the checklist as you go.
`references/other-technologies.md` explains how to add a reference once a template is automated.

## Gather the inputs (one message, up front)

Take what the request already says, then ask for whatever is still missing in a single message, with defaults
filled in. If nobody can answer (a non-interactive run), continue with the defaults and record every assumption
in the checklist header.

| Input | Why it is needed | Default |
| --- | --- | --- |
| Project / app name | App module name (snake_case, e.g. `doer_be_api`) | the current directory's name |
| Client | Checklist header | ask |
| Technology | Picks the reference and the AI config tier | Ruby on Rails |
| GitHub repository (`owner/name`) | Only if it already exists: it gets connected as `origin` and synced through a pull request | none (not created yet) |

Nothing else is asked here. Project routing (Jira, Confluence, Figma, Observer) is collected by `/init-agents` in
step 7, and the template source is the reference's default unless the user explicitly asks for another one.

## Check prerequisites before touching anything

Finding a missing tool halfway through wastes the run, so check everything first and report all gaps in one
message:

- **git works**: `git --version`. A broken binary can sit first on `PATH` (for example an x86-only git on Apple
  silicon, which fails with "Bad CPU type in executable"). Use a working one by absolute path, or put a directory
  with a symlink to it first on `PATH` for commands that call git themselves.
- **Python 3.11+** for the AI config renderer: `python3 --version`. If it is older, `uv run --python 3.12 ...`
  works without a system install, or offer `brew install python@3.12`.
- **Access to the AI baseline**: `git ls-remote git@github.com:coaxsoft/ai_infrastructure.git HEAD`, or
  `gh repo view coaxsoft/ai_infrastructure`.
- **GitHub CLI**, only when a GitHub repository exists or is to be created: `command -v gh && gh auth status`.
  Offer `brew install gh` if it is missing; authentication is interactive, so the user runs `gh auth login`.
- **The technology toolchain** listed in the reference.

Installing software and authenticating are the user's call: offer the command, then wait. Non-interactive shells
often lack the user's shell setup (version managers, Homebrew), so check `echo $PATH` and prefer absolute paths
or the version manager's exec wrapper (`rvm <version> do`, `rbenv exec`, `mise exec`) over bare commands. On
macOS the shell is often zsh, which does not word-split variables: `p="rvm 3.4.7 do"; $p ruby` fails. Spell the
prefix out in each command, or run multi-line snippets with `/bin/bash -c`. The bundled scripts run under bash,
so their `RUBY_RUN` variable is safe.

## Workflow

Track progress in the checklist from step 2 onwards. If `PROJECT_SETUP_CHECKLIST.md` already exists in the
directory, this is a resumed run: read it first, continue from the first unchecked item, and re-verify ticked
items that later changes could have broken, such as boot and tests.

### Step 1: Git and AI configuration (always first)

The AI configuration (`.claude/CLAUDE.md`, rules, skills, the `/init-agents` command) carries COAX's engineering
rules for the technology. Importing it first means the rest of the setup is done the way the team will work.

1. **Initialise git** in the current directory if it is not a repository yet: `git init -b dev`. COAX Git-flow
   uses `dev` as the main branch.
2. **Import the AI configuration, before anything else.**
   - **No GitHub repository yet (the usual case):** do a local first import with the renderer
     `sync-coax-ai-configs` uses, and follow that skill's rules: render, never copy raw canonical files, and
     never pass `--clean`. Clone the baseline into a temporary directory outside the project, render the tier
     into the current directory, and note the baseline commit for the checklist:

     ```bash
     work=$(mktemp -d)
     git clone --depth 1 --quiet git@github.com:coaxsoft/ai_infrastructure.git "$work/infra"
     python3 "$work/infra/tools/render.py" --tech <tier> --tools claude --out .
     git -C "$work/infra" rev-parse --short HEAD
     ```

     Without SSH access, `gh repo clone coaxsoft/ai_infrastructure "$work/infra" -- --depth 1` works too. The
     Claude Code lane (`--tools claude`) is the COAX default; add `copilot`, `cursor` or `antigravity` only if the
     team uses those tools. Commit the result on `dev` as
     `Import AI configuration from ai_infrastructure (<baseline commit>)`, then delete the temporary clone.
   - **The GitHub repository already exists:** connect it as `origin` (if it already has commits, fetch it and
     base `dev` on `origin/dev`), then run the `sync-coax-ai-configs` skill (Skill tool) with the tier. Inference
     would fail because there is no manifest yet. It opens a pull request and deliberately leaves the working
     tree untouched, so continue from its sync branch (`origin/<sync branch>`). A `coaxsoft`-owned repository is
     served by the automated sync workflow instead; that skill will say so.
   - Either way, once the repository exists, `sync-coax-ai-configs` keeps the configuration current. That is a
     checklist follow-up for the owner.
3. **Create the setup branch** `project-setup` from `dev` (or from the sync branch). Everything after this step
   lands there, so the whole setup becomes one reviewable pull request once the repository exists. If the team
   already has a setup ticket, name it `<JIRA-ID>/project_setup` per Git-flow.

Do not write a root `CLAUDE.md`: `/init-agents` creates it together with `AGENTS.md` in step 7.

### Step 2: Create the project setup checklist

Copy [assets/templates/PROJECT_SETUP_CHECKLIST.md](assets/templates/PROJECT_SETUP_CHECKLIST.md) to the project
root as `PROJECT_SETUP_CHECKLIST.md`. Fill in the header table, tick what step 1 achieved (with evidence, such as
the baseline commit), and copy the reference's "Checklist additions" into "Additional items". Commit it as
`Add project setup checklist` before generating the app: the generator writes over many files, and committed
files make any unwanted change show up in `git diff`.

### Step 3: Generate the application

Follow the reference's "Generate" section to generate the app into the current directory. It already holds the
AI configuration and the checklist, so afterwards check `git status` and `git diff` for those committed paths
(`.claude/`, `.claudeignore`, `.gitattributes`, `PROJECT_SETUP_CHECKLIST.md`) and restore or merge anything the
generator overwrote. The reference names the files known to collide.

### Step 4: Configure

Follow the reference's "Configure" section (credentials, generated docs, seed data). Never commit secrets. Key
files stay gitignored, so tell the user where they are and that the team shares them through a password manager.

### Step 5: Verify and iterate until green

Run the reference's verification (for a stack without a full reference, the template's own test, lint and build
commands) before starting the app; the checks against the running app come in step 6. Green means everything in
the reference's definition of green, at minimum:

- the app builds and boots;
- the test suite passes, locally and the way CI runs it;
- the linters and security scans are clean;
- the running app responds: a backend answers its health check, a web front end serves its pages, a mobile app
  launches on a simulator or emulator.

When something fails:

1. Read the actual error and find the root cause before changing anything.
2. Decide where the fix belongs, because that decides what you change and what you record:
   - **Environment** (wrong Ruby, database not running, broken binary on `PATH`): fix how commands are run, or
     tell the user what to install or start. Do not patch the project around a machine problem.
   - **Generated project**: fix it in the project and note it in the checklist's verification log.
   - **Template defect** (any fresh project from this template would hit it): fix it in the project so this
     setup completes, and record it under "Template issues" in the checklist with the fix the template needs.
3. Re-run the whole verification, not just the failing command, because fixes interact.

Do not reach green by weakening checks: no skipping or deleting specs, disabling cops, or loosening security
settings unless the user agrees and the checklist records why. If the same failure survives three honest
attempts, stop and ask, showing what you tried.

### Step 6: Run the app and run the green verification

Start the app with the reference's command, detached so it outlives this session, and wait until it responds:

- backend: the dev server answers its health check;
- web front end: the dev server serves the app;
- mobile: the bundler is running and the app is launched on a simulator or emulator.

Then run the full verification again, including the checks against the running app. This run is the one that
counts as green; record it in the verification log. Leave the app running, and give the user its URL (or the
simulator it runs on) and the restart command.

### Step 7: Create AGENTS.md with /init-agents (required)

`AGENTS.md` is the project's own memory file, and the setup is not done without it. Run the `/init-agents`
command synced in step 1. If the slash command is not loaded in this session (it arrived after the session
started), read `.claude/commands/init-agents.md` and follow it as written. It runs now, after the app exists,
because it reads the codebase for the build and test commands. It:

- checks the MCP connectors (Atlassian, Observer, and Figma for apps with a UI) and walks the developer through
  connecting any that are missing;
- asks the developer for the routing links (Jira, Confluence, Figma, Observer, related repos) and the project
  description;
- writes `AGENTS.md`, and the root `CLAUDE.md` that imports `AGENTS.md` and `.claude/CLAUDE.md`.

Pass it the build, test and run commands verified in steps 5 and 6. Anything the developer cannot answer becomes
`TODO(...)` in `AGENTS.md`: the file must still exist. Tick the checklist item when it does, noting any open
TODOs as partial with the owner.

### Step 8: Work through the remaining checklist items

Do the items that can be done and verified locally (the reference says which: Git-flow branches, git hooks, CI
workflow, Docker, README content). Items that need the GitHub repository, SonarQube or a person stay unticked
with an owner, for example "DevOps: create SonarQube project". Anything that changes a remote system (creating
the repository, pushing, SonarQube, repository settings) needs the user's go-ahead first.

### Step 9: Commit

Commit the setup on `project-setup` (`Project setup`). If the items after step 6 changed code or config, re-run
the verification first. Restore files the verification rewrote without a real change (the reference says which).
Update the checklist last and commit it, so the committed checklist matches the committed code.

Nothing is pushed by default. Once the repository exists, and only with the user's go-ahead: push `dev` and
`project-setup` (plus `staging` and `production`), make `dev` the default branch, open the pull request
`project-setup` into `dev` for the competence lead's review, and connect the AI config sync.

## Checklist protocol

`PROJECT_SETUP_CHECKLIST.md` is the single source of truth for setup progress. Teammates read it in the pull
request, and a resumed run starts from it.

- Update it right after each item is verified, not in a batch at the end, so an interrupted run leaves an
  accurate record.
- Tick `[x]` only on evidence. Append ` - done YYYY-MM-DD: <evidence>`, such as a command and its result, a file
  path or a commit. "Should work" is not evidence. Refer to commits by message ("in the setup commit") rather
  than by a hash that is not final yet.
- Use `[-]` for not applicable, with the reason.
- An item that needs a person stays `[ ]` with ` -> <owner>: <what is needed>`.
- An item that is done here but not finished stays `[ ]` with ` - partial YYYY-MM-DD: <what is done>` and
  ` -> <owner>: <what remains>`, for example branches created locally that are not pushed yet.
- Items about the competence lead can be ticked when the requester says they are the competence lead; cite that.
- Never delete items. Project-specific extras go under "Additional items".
- Add a row to the verification log for every verification run, failed runs included, so the history of fixes
  is visible.
